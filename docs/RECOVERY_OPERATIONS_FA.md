# پشتیبان و بازیابی سکنا

## مدل عملیاتی واحد
سکنا یک مسیر پشتیبان‌گیری دارد. دکمه «گرفتن پشتیبان جدید» و Worker خودکار دقیقاً همان فرمت را می‌سازند. نقطه بازگشت کوتاه‌مدتی که پیش از Restore ساخته می‌شود جزئیات داخلی موتور بازیابی است و در پنل به‌عنوان نوع دوم Backup نمایش داده نمی‌شود.

هر فایل `sokna-backup-*.tar.gz` شامل وضعیت لازم برای بازسازی کسب‌وکار است:
- پایگاه داده کامل؛
- فایل‌های `uploads`؛
- هویت داخلی لازم برای بازشدن تنظیمات محرمانه پس از انتقال سرور.

کد برنامه، cache، session، logهای موقت و مشخصات اتصال دیتابیس/URL سرور مقصد داخل وضعیت قابل‌انتقال قرار نمی‌گیرند. کد از Clean Install/Update رسمی همان نسخه تأمین می‌شود و تنظیمات محیطی سرور جدید حفظ می‌شوند.

فایل Backup شامل اطلاعات کامل کسب‌وکار است و باید مانند اسناد مالی محرمانه نگهداری شود.

## ساخت خودکار و نگهداری
- Worker باید حداقل ساعتی اجرا شود؛ اگر آخرین Backup سالم کمتر از ۶ ساعت عمر داشته باشد کاری انجام نمی‌دهد.
- حداکثر فاصله هدف بین Recovery Pointهای عادی: ۶ ساعت.
- ۲۸ Backup اخیر روی سرور نگهداری می‌شوند؛ تقریباً ۷ روز پوشش با چهار نقطه در روز.
- آخرین نسخه سالم، حتی اگر خارج از ۲۸ فایل تازه باشد، تا زمانی که نسخه سالم جدیدتری وجود نداشته باشد حذف نمی‌شود.
- حداکثر ۵ نقطه بازگشت داخلی Restore نگهداری می‌شود.
- حداقل هفته‌ای یک نسخه سالم باید خارج از همان سرور نگهداری شود. پنل در صورت عقب‌افتادن این کار هشدار می‌دهد.

وجود فایل به‌تنهایی نشانه سلامت نیست. هر Backup پس از ساخت با همان Validator مسیر Restore، شامل Manifest، فهرست دقیق فایل‌ها و SHA-256 هر Entry، بررسی می‌شود و فقط پس از PASS «سالم» محسوب می‌شود.

## انتقال به سرور جدید
مسیر پشتیبانی‌شده برای مدیر:
1. روی سرور قدیمی «گرفتن پشتیبان جدید» را اجرا و از سالم بودن آن مطمئن شوید.
2. همان فایل را دانلود و خارج از سرور نگه دارید.
3. Clean Install **همان نسخه سکنا** را روی سرور جدید نصب کنید و اتصال DB/URL مقصد را تنظیم کنید.
4. وارد «پشتیبان و بازیابی» شوید و همان فایل را بارگذاری کنید.
5. سکنا فایل را پیش از هر تغییر کامل اعتبارسنجی می‌کند؛ سپس «بازگرداندن اطلاعات» را تأیید کنید.
6. قبل از اعمال Backup، موتور یک نقطه بازگشت داخلی از نصب مقصد می‌سازد.
7. DB و uploads بازیابی می‌شوند، هویت داخلی لازم خودکار منتقل می‌شود و تنظیمات فنی سرور جدید دست‌نخورده می‌مانند.
8. Health Check اجرا می‌شود. در صورت خطا، موتور تلاش می‌کند به نقطه قبل از Restore برگردد؛ اگر آن بازگشت هم ناموفق باشد سامانه Fail-closed در وضعیت `recovery_required` می‌ماند.
9. پس از Restore موفق، Session نصب قبلی پایان می‌یابد و ورود مجدد با کاربران بازیابی‌شده الزامی است.

مدیر در هیچ مرحله‌ای با `app.key`، SQL، SSH یا ویرایش دستی `config.php` مواجه نمی‌شود.

## محدودیت نسخه
Restore مدیریتی فقط روی همان نسخه Web و schema سازگار انجام می‌شود. این محدودیت عمدی است: بازیابی داده و Upgrade دو عملیات پرریسک مستقل‌اند و نباید در یک مرحله مبهم ترکیب شوند. ابتدا همان نسخه را Restore کنید و سپس از Updater رسمی ارتقا دهید.

## Restore و چاپ
پیش از جابه‌جایی برنامه‌ریزی‌شده سرور، صف چاپ باید drain/reconcile شود. Backup وضعیت Server را حمل می‌کند اما شواهد محلی Windows Spooler/Agent ممکن است جلوتر از Snapshot سرور باشند. Job با نتیجه مبهم پس از Restore نباید خودکار دوباره چاپ شود.

## آزمون قبل از Production
قبل از Go-Live حداقل یک Drill واقعی لازم است:
- ساخت Backup از محیط آزمایشی؛
- Clean Install همان نسخه روی Clone جدا؛
- Upload و Restore از UI؛
- ورود با کاربران بازیابی‌شده؛
- بررسی میزها، سفارش‌ها، فاکتورها، موجودی، فایل‌ها، قالب‌ها و گزارش‌ها؛
- بررسی اتصال‌های رمزگذاری‌شده؛
- بررسی صف چاپ بدون reprint خودکار.

این Drill در محیطی که MySQL/MariaDB واقعی در دسترس نیست `NOT_RUN` است و نباید PASS اعلام شود.
